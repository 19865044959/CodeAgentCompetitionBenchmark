## 三、分工程失败模式与根因

### 1. CLI工具 — 20 次失败,全部是 A 类(答案写错目录)

**根因**: GA 的 `code_run` 默认 cwd 是 **GA 自己的 temp 目录**(`/mnt/d/work/Hackthon/GenericAgent/temp`,ga.py:23),模型用不带路径的相对文件名写答案 → 落在 GA/temp,评测端在任务目录找不到。

- GA 日志铁证: `write answer_e1.json. CWD: /mnt/d/work/Hackthon/GenericAgent/temp`(7 次出现);模型自述"已保存至 /mnt/d/work/Hackthon/GenericAgent/temp/answer_e2.json"。
- **时间因素**: 20 次失败全部发生在 8-14 10:27 prompt 绝对路径修复**之前**的轮次(qwen3.5 的 21:29–01:00 轮、qwen3.6-35b 的 02:14–04:36 轮)。修复后跑的 deepseek(10:26 之后)CLI 0 失败。
- **结论**: 属"题目表述 + GA 默认 cwd"叠加缺陷,已被 prompt 修复覆盖;需重跑 qwen3.5/3.6 验证。根治方案在 GA 侧: code_run 默认 cwd 改为任务目录。

### 2. 未知API — 21 次失败,工程自带的"过时文档"陷阱为主

这是 6 个工程里**唯一能同时难倒四个模型**的工程(题3 合计正确率仅 50%)。题目故意让 API 文档过时:文档中"查询所有"的示例指令**已被损坏**,并宣称北京"应当返回 15 条",而实际 API 分页为 10 条/页。

- **B 类 oldest_era 错 11 次(三模型全中招)**: era 字段是朝代字符串(商周/战国/唐/清…),需按朝代先后排序。正确答案 成都最早 = **金沙遗址(商周)**,但模型多次误报 都江堰(战国)/武侯祠/望江楼/杜甫草堂。DeepSeek 某一轮甚至自己推理出"都江堰(公元前256年)不是最早",却仍提交了都江堰——说明是**朝代→年代换算的排序错误**,而非没看到数据(日志显示数据行 `CD003: 金沙遗址 | era=商周` 都在上下文里)。
- **B 类 total_count 错 5 次(全部 qwen3.5)**: 期望 15 实报 10(只取了默认第一页,没翻页)、期望 10 实报 20(没按城市过滤/翻页翻重了)——**分页陷阱**,且全在弱模型上。
- **A 类 5 次(qwen3.5)**: 该工程 prompt 8-13 19:49 已加绝对路径,但 qwen3.5 仍有 4 次没写出文件(1–3 turns 就停,WORKING MEMORY 里只有读题摘要)——**不是路径问题,是模型读了题就放弃**。

### 3. 照样板办事 — 12 次失败,规则归纳失败 + 幻觉成功

- **C 类 8 次(全部 qwen3.5)**: 20–47 turns 仍未通过 check,模型自述"无法找到一个统一的排序规则同时适用于两个样本"、"已达到 3 次迭代限制,需请求用户协助"。该工程样板包含**多键排序(站点+日期)+ 价格 ROUND_HALF_UP 转换**等复合规则,qwen3.5 只能归纳出部分规则。
- **D 类 4 次**: 最恶劣的失败模式——**模型声称通过,实际没通过**。例: 题3 提交的 TOKEN 是题1 的(`86b640acad78`,期望 `f9fd09efd173`),把上一题的答案/TOKEN 张冠李戴;qwen3.6-35b 声称"Check1 verification passed",实际 check 输出 `not`。27b 也栽了 1 次同样的题3 张冠李戴。
- 该工程是 4 个 D 类失败的**唯一来源**,且题3 占一半——"复用"被弱模型做成了"照抄"。

### 4. 营地物资统计 — 8 次失败

- A 类 7 次(全部 qwen3.5): 与 CLI 同根因(相对路径 + GA 默认 cwd),且全部在 10:27 prompt 修复前的轮次。
- E 类 1 次(qwen3.5): 写入的 JSON 引号错误(`Expecting property name enclosed in double quotes`),但模型自述"已验证通过"——写入后没做解析校验就宣称完成。

### 5. 工程修复 — 3 次失败,全部 qwen3.5 且全部"提前放弃"

1–5 turns 就停在中间步骤("现在运行检查脚本验证所有修复"之后无下文),未走到 `./check` 输出 TOKEN。不是不会修,是**没坚持到验证那一步**。

## 四、题位规律

| 类别 | 题1 | 题2 | 题3 |
|---|---|---|---|
| A. 未写答案文件 | 11 | 11 | 10 |
| B. 内容与期望不符 | 3 | 3 | **10** |

- **A 类三题均匀**: 是模型"执行习惯"问题(相对路径写文件),与题目难度无关——随 prompt 修复和 GA 侧改进应整体消失。
- **B 类集中在题3**: 题3 换数据源/换统计口径后,泛化能力不足集中暴露(未知API 题3 一个题贡献了 10 次内容错误)。

## 五、结论与建议

1. **梯队**: DeepSeek ≈ Qwen3.6-27B(94.7%)> Qwen3.6-35B-A3B(84.0%)> Qwen3.5-35B-A3B(42.7%,贡献了 43/64 = 67% 的失败,五类原因全占)。
2. **最大单一根因是路径(A 类 32 次),且是可修复的工程问题**: prompt 绝对路径已修(8-14 10:27–10:28),建议立刻重跑 qwen3.5/qwen3.6 的 CLI/营地确认 A 类归零;根治方案是改 GA `code_run` 默认 cwd 为任务目录。
3. **未知API 题3 是全场唯一"第一梯队杀手"**(deepseek/27b 各 40%/60%): 陷阱设计有效,但若统计"泛化能力",可考虑将该题的 oldest_era 单列指标。
4. **弱模型(qwen3.5)的独有失败模式**: 幻觉成功(声称 check 通过但 TOKEN 是别的题的)与提前放弃(1–3 turns 就停)——这类失败对"自进化"评测是噪声,统计时值得单列"模型自报完成 vs 实际完成"的一致性指标。
